# apps/console — agent guide

The Sentient web console. A separate Vite app from `apps/landing`; separate build,
separate origin, no cross-origin token handoff. Landing's Launch CTA is a plain link
to this app's `/auth/sign-in`.

## Commands

```bash
npm run dev     # 127.0.0.1:5175 -- NOT localhost, see below
npm run build   # vite build, then tsc --noEmit
npm run lint    # the layer rules; this app's only gate
npm run test    # vitest: the fetch seam and the SSE parser, nothing else
```

`build` runs `vite build` **before** `tsc --noEmit`, not the other way round:
`src/routeTree.gen.ts` is generated by `@tanstack/router-plugin` during the Vite
build, and it is gitignored. On a fresh clone a typecheck-first order fails on a
file that does not exist yet.

**This app is outside every backend gate.** `ruff`, `mypy`, `import-linter` and `pytest`
are path-scoped to `src/` and `tests/` at the repo root. Nothing here can turn the Python
CI red — and nothing here is covered by it either.

## Layers — dependencies point one way

`routes → features → lib → types`

- `routes/` — file-based routing, layouts, guards, redirects. **No fetching, no business
  logic.** A route may resolve params, call a feature hook, and compose components. A
  `fetch`, a `useState` holding domain state, or a conditional business rule in a route
  file belongs in a feature.
- `features/` — one folder per F item; the only place domain logic lives. Every feature has
  the same shape: `api.ts` (query keys + mutations), `hooks.ts` (the public verbs),
  `components/`, `index.ts` (**the only public surface**).
- `lib/api/` — one typed module per backend resource, plus `client.ts`, the fetch seam.
- `components/ui/` — shadcn primitives. **Domain-free.** A primitive that knows what a
  "project" is has stopped being a primitive.
- `types/` — DTOs mirroring the backend's Pydantic schemas in `src/sentient/api/schemas/`.
  No feature redeclares a backend shape locally; that is how the two drift.

**Features never import each other's internals.** `features/threads` may import
`features/projects` only through `features/projects/index.ts`. Anything two features both
need moves _down_ into `lib/` or `components/ui/` — never sideways. Cross-feature reaching
is how a modular tree quietly becomes a graph.

`npm run lint` enforces the direction. It cannot enforce everything, so also:

- **One file, one purpose.** If you cannot describe a file in one sentence without "and",
  split it. A component over ~150 lines almost always contains a second component.
- **Data fetching lives in `hooks.ts`, never in a component body.** Components receive data
  and callbacks, which is what makes them renderable in isolation.

## The fetch seam

`lib/api/client.ts` is the **only** place that attaches `Authorization`, refreshes an
expired token, and maps HTTP status onto typed errors. Features import a resource module;
**no feature calls `fetch` directly**, and lint fails if one does. This is the frontend's
counterpart to the backend's "routers import the `deps` module, never names out of it".

The lint rule is `no-restricted-globals` on `fetch`, which catches a bare `fetch(...)`.
`window.fetch(...)` and `globalThis.fetch(...)` are closed separately by
`no-restricted-properties`. The ban is written once, as `src/**` minus `src/lib/api/**`,
rather than re-listed per layer, so a layer added later is covered without anyone
remembering to extend it.

**Two gaps, both measured against deliberate violations rather than assumed:**

1. `no-restricted-imports` inspects static `import` declarations only. A dynamic
   `import("@/features/projects/api")` is **not** caught. Verified.
2. Neither rule sees a `fetch` reached through an alias (`const f = fetch`). Verified.

Both are on you. If either starts happening in practice, close it with a rule rather
than another paragraph here.

## Neon Auth — what the SDK actually does

Measured against `@neondatabase/neon-js@0.7.0-beta`, which re-exports
`@neondatabase/auth@0.5.0-beta`. Neon's docs and the F1 plan were each wrong on one
point; these were settled by reading the installed `.d.mts` and by a `tsc` probe, not
by trusting either source. **Re-verify on any version bump.**

| Question                                       | Answer                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| How do you get the backend JWT?                | **`createInternalNeonAuth(url, cfg).getJWTToken()`**. Not `token()`, and not on `createAuthClient`'s result.                                                                                                                                                                                |
| Which factory?                                 | **`createInternalNeonAuth`**, despite the name. Both are exported from the public entry and share one JSDoc block.                                                                                                                                                                          |
| Where does `BetterAuthReactAdapter` come from? | `@neondatabase/neon-js/auth/react/adapters`, not the main entry. Adapters are factory functions: call them with `()`.                                                                                                                                                                       |
| Which package has the prebuilt UI?             | `@neondatabase/neon-js/auth/react/ui`. `@neondatabase/auth-ui` is the same code standalone and arrives as a transitive dep; do not install it directly.                                                                                                                                     |
| Peer dependencies?                             | None to install. `@neondatabase/auth-ui` bundles `@daveyplate/better-auth-ui` and its Radix / react-hook-form / zod / sonner tree transitively. The `react-auth-external-ui` example's long `npm install` list is for using better-auth-ui directly, which we do not.                       |
| CSS                                            | `@import "@neondatabase/neon-js/ui/tailwind";` in `globals.css`, after `@import "tailwindcss";`. The `ui/css` variant is the prebuilt bundle for non-Tailwind apps.                                                                                                                         |
| Which component renders a screen?              | **`AuthView view="SIGN_IN"` / `view="SIGN_UP"`**, not `SignInForm` / `SignUpForm`. Those are inner pieces: they require a `localization` prop `AuthView` supplies, and render neither the card, the title, nor the sign-in/sign-up switch.                                                  |
| Does the provider need `navigate` / `Link`?    | No. Their defaults set `window.location.href`, so the form's own links are full page loads. Wiring TanStack Router needs a cast past its route-union `to` typing; F11 owns it. `basePath` defaults to `/auth` and view paths to `sign-in`/`sign-up`, which already match this app's routes. |

**The trap.** `createAuthClient(url, cfg)` is literally
`createInternalNeonAuth(url, cfg).adapter`. It returns the Better Auth React client and
**discards `getJWTToken`**. Building on it means `authClient.getJWTToken` is `undefined`
at runtime — every backend call goes out unauthenticated and 401s, with nothing in the
browser to explain why. `tsc` catches it as TS2339, which is the only reason it is cheap
to find.

**The second trap.** `NeonAuthPublicApi<T>` is a conditional type whose **vanilla** branch
matches the React adapter first, so `neonAuth.adapter` is typed as the vanilla client —
where `useSession` is a nanostores atom, not a hook. Calling it is TS2349. `lib/auth.ts`
therefore builds the adapter itself and takes `adapter.getBetterAuthInstance()`, which is
typed `ReactAuthClient` and is the same object at runtime. That is why the config is
`{ adapter: () => adapter }` rather than `{ adapter: BetterAuthReactAdapter() }`: one
adapter instance, so one Better Auth client and one session store. Do not "simplify" it
back; you get two clients or a cast.

So `lib/auth.ts` exports two things from one `createInternalNeonAuth` call:
`authClient` (the `.adapter`: `useSession`, `signIn`, `signUp`, `signOut`, and what
`NeonAuthUIProvider` wants) and `getAccessToken()` (the `.getJWTToken`).

**Do not pass `fetchOptions: { credentials: "include" }`.** It is not on the public
config type, and Better Auth's own client config already sets `credentials: "include"`
whenever the browser supports it.

## Two things that will bite you

1. **`127.0.0.1`, never `localhost`.** Uvicorn binds IPv4 only; Windows resolves
   `localhost` to `::1` first. Measured: 208 ms wasted per request, invisible in the
   server's logs. This applies to `VITE_API_BASE_URL` and to the Mantella URL this app
   tells users to paste.
2. **Never hardcode a Neon Auth URL.** Every Neon branch gets its **own** auth environment,
   so a literal URL is correct for exactly one branch. Get it from `neon env pull` and read
   it from `VITE_NEON_AUTH_URL`.

## Streaming

Read SSE with `fetch` + a `ReadableStream` reader, **not `EventSource`** — `EventSource`
cannot issue a POST and cannot set an `Authorization` header. It is the obvious API and the
wrong one here.
